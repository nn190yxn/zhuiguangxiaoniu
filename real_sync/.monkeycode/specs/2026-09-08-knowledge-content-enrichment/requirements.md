# 知识卡内容增强需求

## 目标

基于后台保存的知识卡完整原文，为内容较短或结构缺失的卡片补充教学说明、操作细节和安全边界，并保留原文、增强稿和发布版本的独立追溯关系。

## 术语

- **原文**：知识卡当前或历史版本中保存的完整 `content`。
- **增强稿**：基于原文整理出的结构化教学内容，包含可追溯的原文依据。
- **发布稿**：经过审核并对员工端可见的增强稿版本。
- **增强任务**：一张知识卡的一次扫描、生成、审核或发布记录。

## 需求

### 需求1：原文保护与版本追溯

**用户故事：** 作为内容管理员，我希望增强内容保留原文和版本关系，以便核对事实并回退内容。

#### 验收条件

1. 当系统创建增强稿时，系统应保存源知识ID、源版本ID和源正文SHA256。
2. 当源版本或正文SHA256发生变化时，系统应将增强稿标记为需要重新审核。
3. 当员工查看知识卡时，系统应优先展示已发布增强稿，并提供原文查看入口。
4. 当增强稿回退时，系统应恢复上一版发布稿或原始正文。

### 需求2：内容质量扫描

**用户故事：** 作为内容管理员，我希望系统识别内容空缺，以便优先处理最需要增强的卡片。

#### 验收条件

1. 当系统扫描已发布知识卡时，系统应检查正文长度、段落数量、摘要、步骤、教练提示和安全说明。
2. 当卡片缺少一个或多个质量字段时，系统应创建增强任务并记录缺失字段。
3. 当同一知识版本重复扫描时，系统应产生稳定的缺失字段和任务分层结果。
4. 当正文为空时，系统应标记为原文缺失并进入人工处理状态。

### 需求3：分类型增强

**用户故事：** 作为教练，我希望不同类型的知识卡拥有合适的结构，以便直接用于备课和授课。

#### 验收条件

1. 当卡片属于动作类型时，增强稿应包含目标、准备、步骤、教练提示、常见错误、难度调整和安全边界。
2. 当卡片属于感觉统合类型时，增强稿应包含感觉目标、输入方式、观察反应、调节方式、课堂支持和专业边界。
3. 当卡片属于体能类型时，增强稿应包含训练目标、强度、组数、时间、休息、进阶标准和停止条件。
4. 当卡片属于教学方法、儿童发展或家长沟通类型时，增强稿应包含适用场景、操作流程、观察指标或沟通示例。

### 需求4：事实约束与风险标记

**用户故事：** 作为教学负责人，我希望增强内容有事实依据并标记风险，以便控制错误教学和过度医疗化表达。

#### 验收条件

1. 当增强稿包含原文未明确的参数、医学判断或发育结论时，系统应标记人工确认状态。
2. 当增强稿无法提供原文依据时，系统应保存待确认原因并阻止直接发布。
3. 当内容涉及极限拉伸、高强度训练、异常反应或专业转介时，系统应显示对应风险标记。
4. 当增强稿被审核通过时，系统应保存审核人、审核时间、审核意见和审核前后哈希。

### 需求5：后台审核与发布

**用户故事：** 作为内容管理员，我希望在后台对原文和增强稿进行对照审核，以便控制发布质量。

#### 验收条件

1. 当管理员打开增强任务时，系统应并排显示原文、增强稿、原文依据和风险标记。
2. 当管理员编辑增强稿时，系统应保存字段级变更并增加状态版本。
3. 当管理员通过增强稿时，系统应将稿件置为可发布状态并保留审核记录。
4. 当管理员退回增强稿时，系统应要求填写原因并保留退回记录。

### 需求6：员工端展示与降级

**用户故事：** 作为员工，我希望看到完整、易用且可信的知识内容。

#### 验收条件

1. 当发布稿存在时，详情页应展示发布稿并标识增强版本。
2. 当发布稿不存在时，详情页应展示原文。
3. 当增强稿生成失败或处于审核中时，员工端应继续展示原文并显示明确状态。
4. 当列表页加载知识卡时，系统应使用增强摘要，并在增强摘要缺失时使用现有摘要逻辑。

### 需求7：批量发布与回退

**用户故事：** 作为平台管理员，我希望按批次发布和回退增强内容，以便安全运营。

#### 验收条件

1. 当系统发布增强批次时，系统应校验知识ID、版本ID、正文SHA256、引用完整性和审核状态。
2. 当任一发布校验失败时，系统应阻止该条记录进入发布批次并记录失败原因。
3. 当管理员执行批次回退时，系统应恢复批次发布前的有效内容。
4. 当批次处理完成时，系统应输出成功、待审核、失败和风险数量。
