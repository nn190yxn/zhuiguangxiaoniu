# 需求文档

## 目标

建立一套固定流程，使服务器、本地代码和 GitHub 保持可核对的状态。服务器当前正常运行的功能作为业务基线；本地未部署的架构升级能力先完成验证，再进入独立发布批次。

## 名词说明

- **生产服务器**：当前用户实际使用的网站，目录为 `/www/wwwroot/122.51.223.46/`。
- **本地工作区**：用于审计、合并和自动化测试的代码副本。
- **GitHub 基线**：远程仓库中可追溯、可恢复的已确认版本。
- **发布批次**：一组明确文件、备份、验证和回滚步骤组成的小范围生产变更。

## 需求

### 需求 1：服务器优先的版本裁决

**用户故事：** 作为维护者，我希望每次同步都先确认服务器实际状态，从而保护当前正常使用的功能。

#### 验收标准

1. 当发现服务器、本地和 GitHub 文件内容不同，系统应记录三个版本的修改时间、摘要和来源。
2. 当服务器功能已由实际使用或生产验证确认，系统应将服务器文件标为默认保留来源。
3. 当本地文件包含未部署能力，系统应将本地文件标为候选升级来源，并记录对应测试证据。

### 需求 2：先同步到本地，再同步到 GitHub

**用户故事：** 作为维护者，我希望先在本地拼出完整可测试版本，再推送 GitHub，从而让 GitHub 成为可靠版本库。

#### 验收标准

1. 当服务器存在本地缺失的正常运行功能，系统应先将该功能以逐文件方式回收至本地。
2. 当本地合并完成，系统应执行相关自动化测试和 PHP 语法检查。
3. 当测试通过且差异清单已确认，系统应提交并推送本地版本到 GitHub。

### 需求 3：架构升级采用独立验证和小批量发布

**用户故事：** 作为维护者，我希望把未部署的架构升级与现网功能分开验证，从而避免影响正在使用的页面。

#### 验收标准

1. 当本地架构升级与服务器实现不同，系统应分别记录功能目的、测试结果和生产影响范围。
2. 当候选升级涉及登录、PWA、AI、体测或工作量，系统应建立独立发布批次。
3. 每个发布批次应包含精确文件清单、变更前备份、验证命令、观察时间和回滚步骤。

### 需求 4：每次开发结束必须闭环

**用户故事：** 作为维护者，我希望每次开发都有明确状态，从而随时知道哪个版本可用、哪个版本待发布。

#### 验收标准

1. 当本地代码发生业务变更，系统应更新变更清单并记录测试结果。
2. 当生产发布完成，系统应记录生产文件摘要、发布时间和验收结果。
3. 当 GitHub 推送完成，系统应记录提交号、远程分支和生产对应关系。
4. 当存在未推送或未部署变更，系统应在状态清单中明确标为待处理。
5. 当本轮工作收尾，系统应确认服务器、本地和 GitHub 对应同一确认版本，并记录生产核心功能验证通过的证据。
