# 销售培训知识卡一期导入设计

- 日期：2026-08-24
- 作者：Monkeycode
- 状态：已完成方案确认，待实施计划
- 范围：75 张销售 Markdown 母卡导入培训系统；1417 张训练知识卡不在本期

## 1. 目标与成功标准

将本地 `SALES-0001` 至 `SALES-0075` 的销售培训卡拆分为 K/S/D/C 四类培训卡，导入线上 `training_modules` 与 `training_cards`，同时满足：

1. 不覆盖线上已有 7 个模块和 56 张培训卡。
2. 每张母卡可通过固定编码追溯，重复执行不会重复插入。
3. 默认只预演；正式导入前备份，正式导入使用事务和数据库命名锁。
4. 销售员工可访问，非销售普通员工不可访问，管理身份可按既有管理规则查看。
5. 页面展示结构化排版，不裸露 HTML 标签，不允许脚本注入。
6. 可按本次固定模块编码和卡片编码精确回滚。

## 2. 已确认的现网基线

截至设计日，线上数据为：

- `training_modules`：7 条。
- `training_cards`：56 条。
- `knowledge_items`：194 条。
- 线上与 75 张本地销售卡精确同名 0 条；标题相似度不低于 80% 的仅 `ACE 体系` 与 `ACE评估体系`；内容相似度不低于 40% 的为 0 条。
- `training_modules.module_code` 和 `training_cards.card_code` 均有唯一索引 `uk_code`。
- `training_cards.card_type` 只允许 `K`、`S`、`D`、`C`。
- `training_cards.options` 为 JSON 字段。

兼容约束：

- 员工真实岗位代码为 `sales`，但 `getTrainingModuleRoleCode()` 会将其映射为培训模块历史代码 `consultant`。新模块的 `role_code` 必须写 `consultant`，不能写 `sales`。
- 培训模块只有 `level`，没有员工阶段访问字段，现有培训接口也没有阶段过滤。本期不新增阶段权限模型。
- 当前模块列表已有角色过滤，但模块详情、卡片列表和卡片详情存在仅凭 ID 访问的缺口。本期必须先统一补齐服务端鉴权，不能只在页面隐藏入口。

## 3. 总体方案

采用“本地生成 JSON 数据包 + 服务器 PHP CLI 导入器”的两段式方案：

```text
75 张 Markdown
  -> 本地生成器：解析 frontmatter 与固定章节、校验、生成纯文本字段
  -> sales-training-cards.v1.json + 解析报告
  -> 服务器 PHP CLI：require api/config.php，调用 getDB()
  -> dry-run：结构、冲突、差异、数量和权限配置检查
  -> --apply：命名锁 + 事务 + 3 个模块 + 300 张卡
  -> 验证报告与回滚清单
```

数据库密码、服务器凭据和 SSH 私钥不得进入代码、JSON、日志或 Git。私钥仅用于本机 SSH 客户端连接。

## 4. 模块设计

新增三个模块：

| module_code | module_name | 母卡范围 | level | role_code | category |
|---|---|---:|---|---|---|
| `sales-ability-foundation` | 销售能力·初阶 | 0001-0025 | `beginner` | `consultant` | 销售能力 |
| `sales-ability-advanced` | 销售能力·中阶 | 0026-0046 | `intermediate` | `consultant` | 销售能力 |
| `sales-ability-expert` | 销售能力·高阶 | 0047-0075 | `advanced` | `consultant` | 销售能力 |

- `required_score=60`、`status=1`。
- `sort_order` 使用当前最大值之后的连续值，不占用或改写旧模块顺序。
- `total_cards` 在成功写入卡片后按数据库实际数量重算，不能信任数据包声明值。
- `level` 仅表达学习路径，不作为本期硬权限。所有销售均可看到三个级别。

## 5. 拆卡与字段映射

每张母卡拆为四条：

| Markdown 章节 | card_type | card_code 示例 | 主要字段 |
|---|---|---|---|
| 核心要点 | K | `sales-0001-k` | `content=章节正文` |
| 标准话术 | S | `sales-0001-s` | `standard_answer=标准话术正文`；`content=适用主题说明` |
| 演练场景 | D | `sales-0001-d` | `content=场景与任务要求`；可提取的正确示范写入 `standard_answer` |
| 通关标准 | C | `sales-0001-c` | `content=评分标准`；检查项写入 `options` |

共同规则：

- `title`：`<母卡标题>｜知识/话术/演练/通关`。
- `difficulty`：初阶 `easy`，中阶 `medium`，高阶 `hard`。
- `score=100`；模块及格线仍为 60。源卡出现的评分表保留在内容中，不将单项等级分数误写成卡片总分。
- `sort_order = 母卡数字编号 * 10 + 类型序号`，类型序号 K/S/D/C 分别为 1/2/3/4。
- `status=1`。
- `tips` 保留 `SALES-xxxx`、源文件相对路径、`source_articles` 和来源说明，确保可追溯。
- `options` 必须是 JSON 字符串数组；没有可靠检查项时写 `NULL`，不能伪造选项。

生成器必须验证 75 个唯一 `card_id` 连续覆盖 0001-0075，标题和四个必需章节均可解析。任何母卡缺章节、重复编码、空标题、非法 JSON 或字段超长，都使整次生成失败，不输出可应用的数据包，不能静默跳过。

## 6. 内容与安全展示契约

数据库保存结构化纯文本，不保存来源 Markdown 产生的任意 HTML。页面通过受控格式化函数生成安全 HTML：

1. 动态文本先统一 `escapeHtml()`。
2. 再识别换行、章节标题、有序/无序列表、引用、正确/错误提示和简单评分表，输出限定标签。
3. 不允许来源内容注入 `script`、事件属性、`style`、`iframe`、任意链接或图片。
4. JSON 数据不得直接拼接进 HTML 属性；选项显示和 `data-value` 分别按上下文安全编码。

本期只增强培训卡页面 `training-card.html` 的排版。知识库 H5 与小程序的 HTML 内容契约不在本期改动范围，因为销售卡最终选择导入培训系统。

## 7. 角色鉴权

服务端以模块 `role_code` 为资源权限来源：

- 销售员工：`sales` 经兼容映射后为 `consultant`，允许访问本期三个模块及其卡片。
- 普通非销售员工：禁止访问本期模块列表、详情和卡片。
- JWT 管理身份：按现有 `admin`/`manager` 规则允许管理查看；查询指定角色时继续使用现有受控 `role` 参数。
- `operation`、`ceo` 等岗位若没有 JWT 管理身份，不因岗位名称自动获得培训模块越权访问。本期不扩大管理角色定义。

鉴权必须覆盖：

1. 模块列表。
2. 模块详情及模块卡片列表。
3. `training-cards.php` 的列表、单卡读取、提交和重置。

对无权限资源统一返回无权访问或不存在，不返回卡片正文。前端隐藏不构成权限控制。

## 8. 幂等、差异与冲突策略

以固定 `module_code` 和 `card_code` 为主键语义：

- 编码不存在：计划新增。
- 编码存在且规范化内容完全一致：跳过。
- 编码存在但内容不同：dry-run 标记为待更新；只有显式 `--apply --allow-update` 才更新。
- 编码不同但规范化标题或内容高度相似：列入人工复核，不自动覆盖或合并。
- 本期默认正式命令只新增，不更新旧数据。

差异比较至少覆盖模块归属、类型、标题、内容、选项、标准答案、提示、难度、分值、排序和状态。不得只比较标题。

## 9. 导入、备份与回滚

CLI 默认 dry-run，只有 `--apply` 才写入。正式流程：

1. 校验运行环境为 CLI、数据包版本和 SHA-256、线上表结构及唯一索引。
2. 获取数据库命名锁；获取失败立即退出。
3. 在服务器受限备份目录导出 `training_modules`、`training_cards` 及相关 `user_progress` 的导入前快照；备份失败禁止继续。
4. 开启事务，再次检查冲突。
5. 创建或确认三个固定模块，插入新卡，重算 `total_cards`。
6. 执行事务内断言：模块数、各类型数量、唯一编码、模块归属和外键引用均正确。
7. 提交事务并释放锁，写出不含敏感信息的结果清单。

任何步骤失败必须回滚事务并返回非零退出码。

回滚器默认预演，正式回滚要求显式 `--apply` 和本批数据包 SHA-256。它只删除 `card_code` 属于数据包的记录，并仅在没有非本批卡片、没有用户进度引用时删除三个模块；发现用户进度或未知卡片时停止并报告，不能级联误删。导入前快照作为最终恢复手段，不作为首选回滚方式。

## 10. 测试与上线验收

### 自动检查

- 解析：75 张母卡、75 个 K、75 个 S、75 个 D、75 个 C。
- 编码：300 个 `card_code` 唯一且格式正确。
- 字段：标题不超过 200，编码不超过 50，枚举合法，`options` 为有效 JSON 数组。
- 安全：含 `<script>`、事件属性、引号、尖括号等测试文本只能作为文字显示。
- 幂等：同一数据包连续 dry-run；应用一次后再次 dry-run，应全部为跳过、无新增。
- 权限：销售可访问；普通教练不可通过列表、模块 ID、卡 ID 或提交接口访问；JWT 管理身份可查看。

### 上线顺序

1. 对比线上同路径代码与仓库，确认线上为真实基线。
2. 先部署鉴权修复、页面安全格式化和 CLI 工具，不导入数据。
3. 执行线上 dry-run，保存新增/更新/跳过/冲突报告。
4. 经人工确认报告后执行备份和 `--apply`。
5. 核验模块和卡片数量、`total_cards`、数据库约束与服务端日志。
6. 按初/中/高阶各抽 K/S/D/C 一张，共 12 张，检查排版、内容和操作。
7. 用销售、教练、管理三类测试身份完成权限验收。

## 11. 本期不做

- 不导入 1417 张训练知识卡。
- 不改写线上已有 7 个模块和 56 张卡。
- 不建立员工阶段硬权限或数据库阶段字段。
- 不把全部销售卡同步到 `knowledge_items`。
- 不将旧的相似主题内容自动合并、覆盖或删除。
- 不提交私钥、数据库凭据、线上备份或含敏感信息的运行日志。

## 12. 二期入口

一期验收稳定后，再单独为 1417 张训练知识卡设计分类、角色、阶段和知识库/培训系统落点。二期必须复用本期的生成、dry-run、幂等、备份、事务和回滚框架，但不得默认沿用销售卡的 K/S/D/C 拆分规则。
